# ADR-0002: Poetry Layout Schema and Editing Model (Couplets, Stanzas, Ghazals)

## Status

Proposed

## Context

UEB-MD needs to represent three distinct verse layouts, each with its own
editing and rendering behavior:

- **`stacked`** — a couplet's two lines (misra), each on its own line,
  centered as a unit. The common default presentation for a single sher.
- **`split`** — a single line's two hemistichs printed at opposite
  margins with a fixed central gutter, matching traditional Urdu
  typesetting. This has no equivalent in any existing markdown extension
  or, as far as we found, any existing open-source rich-text editor's
  node model.
- **`band`** — continuous multi-line stanzas (nazm-style), where
  `align=justify` needs to mean "the block's outer margins align with
  surrounding prose" without stretching individual short verse lines the
  way justified prose paragraphs stretch.

On top of individual couplets, a **ghazal** groups a sequence of
independent couplets sharing a radif/qafiya, with `matla`/`maqta`
markers on the opening/closing couplet and an optional poet attribution
line.

This sits on top of ADR-0001's general decisions (extend existing nodes
before adding new ones; `remark-directive` for container syntax) but
needs its own record because, unlike every other UEB-MD feature, poetry
has no existing library, markdown convention, or prior Likhari node to
extend from cleanly. `PoetryBlockNode` already exists in the schema but
was defined before these three layouts and the ghazal/hemistich
requirements were specified, so its shape needs to be decided here
rather than assumed.

Getting this wrong is costly in a specific way other UEB-MD features
aren't: once authors have real ghazals and nazms saved in a given schema
shape, changing that shape means a data migration across every existing
document, not just a converter update.

## Decision

**1. Represent all three layouts as one extended `PoetryBlockNode`, with
a `layout` field, not three separate node types.**

`stacked`, `split`, and `band` are presentation variants of the same
underlying content model — a couplet or stanza is still fundamentally an
ordered set of lines belonging together as one verse unit. Splitting
them into `StackedCoupletNode`/`SplitCoupletNode`/`BandNode` would
duplicate the shared behavior (selection, editing commands, insertion,
serialization) three times for a difference that's purely about layout,
which is exactly the kind of node-type proliferation ADR-0001 already
decided against for footnotes/endnotes and alignment.

**2. Store `split`-layout lines as hemistich pairs (`[right, left]`
tuples), not as plain text with a delimiter parsed at render time.**

The alternative — storing `"right hemistich | left hemistich"` as a
single text line and splitting on `|` at render/edit time — was
considered and rejected. Editing a `split` couplet needs independent
cursor/selection behavior in each hemistich (a user editing the left
half shouldn't have their cursor jump across a text-based delimiter),
and storing structure explicitly avoids re-parsing on every edit. The
`|` delimiter is still what authors type in raw Markdown import/export
(per the UEB-MD spec), but internally, `PoetryBlockNode` in `split` mode
stores each line as a pair, not a single string.

**3. Add a per-line `alignOverride` field, independent of the
container's `layout` and `align` attributes.**

Container-level `align` (e.g. `justify` on a `band`) controls the
block's outer margins; `alignOverride` on an individual line lets an
author right- or left-align one line within an otherwise
center-aligned couplet. These are orthogonal controls and are modeled as
separate fields rather than one combined enum, since collapsing them
would force encoding every combination (block-justify + line-right,
block-center + line-left, etc.) into a single flattened value space that
would need to be re-decomposed on every access anyway.

**4. Introduce two new node types — `GhazalContainerNode` and
`AttributionNode` — rather than extending `PoetryBlockNode` further.**

Unlike the three layouts, a ghazal is structurally different from a
couplet: it's a *collection* of couplet nodes plus metadata (`radif`)
and per-child marks (`matla`/`maqta`) that don't make sense on a single
couplet in isolation. This is a genuine new structure, not a variant of
an existing one, so it gets its own container node per the ADR-0001
principle of adding new types only where nothing existing fits.
`AttributionNode` is a small leaf-ish node for the poet's byline,
separated out because it needs distinct styling/positioning (right-
aligned, below the last couplet) and shouldn't be conflated with a plain
paragraph inside the ghazal container.

**5. Validate the `split`-layout rendering approach with a throwaway
prototype before committing the schema, and treat this phase as a
mandatory pre-merge checkpoint — not a normal phase checkpoint.**

The two-column, fixed-gutter rendering for `split` interacts with
script-aware typography (Nastaliq vs. Naskh line-height, established in
the design spec) in a way that's hard to validate on paper. The
prototype is built as a static, non-editable renderer against real
fixture couplets, entirely outside Lexical, specifically so the CSS/
typography approach is proven before the editable node schema —
including the hemistich-pair storage decision in (2) — is finalized.
This is a stricter gate than other UEB-MD phases get, consistent with
ADR-0001's decision to single out poetry as the one feature requiring
it.

**6. Editing commands are layout-aware but share one insertion entry
point.**

A single "insert couplet" toolbar action inserts a `PoetryBlockNode`
defaulting to `layout: stacked`; a layout switcher control (not a
separate insert command per layout) changes `layout` on the selected
block afterward. This mirrors how the block already needs to support
switching layouts on existing content, not just choosing one at creation
time — an author reformatting a nazm from `band` to individual `stacked`
couplets is a normal editing operation, not a document recreation.

## Consequences

**Positive**

- One node type for all three layouts keeps editing commands, selection
  behavior, and serialization logic in one place; layout-specific
  behavior is a `switch` on the `layout` field rather than three parallel
  implementations.
- Explicit hemistich-pair storage means `split`-layout editing has
  correct per-hemistich cursor/selection behavior from the start, rather
  than needing a follow-up fix once delimiter-based text editing proves
  awkward in practice.
- Separating `alignOverride` from container `align` avoids a combinatorial
  enum and keeps both controls independently discoverable in the
  toolbar.
- The ghazal/attribution split keeps `PoetryBlockNode` itself from
  absorbing collection-level concerns (radif, matla/maqta) that don't
  apply to a standalone couplet.

**Negative / risks accepted**

- `PoetryBlockNode` now carries meaningfully more shape (`layout`,
  per-line `alignOverride`, hemistich-pair storage for `split`) than a
  typical Lexical block node, which raises the bar for anyone extending
  it later — this is accepted as preferable to three separate node
  types duplicating shared behavior.
- Hemistich-pair storage means the raw-Markdown `|` delimiter and the
  in-editor structured representation are two different shapes for the
  same content, so the `converters` package's `split`-layout mapping
  needs explicit test coverage in both directions — this is more parsing
  surface than a plain-text-with-delimiter approach would need.
- The mandatory pre-schema spike adds calendar time before Phase 4 (per
  the implementation plan) can start real node/editing work, on top of
  the phase's own already-planned checkpoint.
- If the spike reveals the two-column `split` rendering doesn't hold up
  under real Nastaliq metrics, the schema decisions here — particularly
  (2) — may need revisiting before any editing UI is built against them.

## Alternatives Considered

- **Three separate node types** (`StackedCoupletNode`, `SplitCoupletNode`,
  `BandNode`) — rejected for duplicating shared editing/serialization
  behavior across layouts that differ only in presentation.
- **Delimiter-based `split` storage** (single text line, `|`-split at
  render time) — rejected due to incorrect cursor/selection behavior
  across the delimiter during editing, and re-parsing cost on every
  edit.
- **A combined alignment enum** covering all block+line alignment
  combinations — rejected as unnecessarily coupling two independent
  controls into one flattened value space.
- **Modeling a ghazal as a plain `LayoutContainerNode`** holding couplet
  children, reusing the existing multi-column node — rejected because
  ghazal-specific metadata (`radif`, `matla`/`maqta` marks) doesn't fit
  a generic layout container without overloading its schema for a
  single, unrelated use case.
- **Skipping the pre-schema spike and iterating on the real schema
  directly** — rejected given the cost of migrating existing documents
  if the `split`-layout approach needs to change after authors have
  real content saved against it.
