# ADR-0001: Adopt UEB-MD Markdown Extension via a Shared remark/unified Pipeline, Split Across Editor and Renderer Packages

## Status

Proposed

## Context

Likhari needs to support authoring and publishing Urdu/Punjabi Shahmukhi
e-books, which requires document features CommonMark/GFM don't cover:
justified text, footnotes, endnotes, appendices, captioned/aligned images,
and poetic couplet/stanza/ghazal layouts with RTL-aware typography.

Two problems needed solving together, not separately:

1. **What markdown syntax represents these features** — there is no
   existing standard for the poetry layouts in particular, so a custom
   extension (UEB-MD) had to be designed.
2. **How that syntax gets parsed, edited, and rendered** — Likhari
   already has a Lexical-based editor with a defined node schema
   (`PoetryBlockNode`, `LayoutContainerNode`, `FootnoteReferenceNode`,
   `PageBreakNode`, `ImageNode`) and a `converters` package responsible
   for Markdown ⇄ Lexical translation. Any new syntax needs to map onto
   that schema without breaking the existing principle that node
   registration is independent of feature flags.

Additionally, exported `.md` files need to be usable outside Likhari
entirely — by a reader app, a static site build, or an EPUB pipeline —
which is a requirement the original architecture didn't explicitly
address, since `converters` was designed for editor round-tripping, not
standalone rendering.

## Decision

**1. Adopt UEB-MD as a CommonMark superset built from existing
conventions wherever one exists, rather than inventing new syntax
across the board.**

- Generic attribute lists (`{#id .class key=value}`) power alignment,
  image sizing/captions, and language tagging — one mechanism, not one
  per feature.
- Fenced container directives (`::: name {attrs}`) handle all
  multi-paragraph/structural constructs: justified blocks, couplets,
  stanzas, ghazals, appendices, and the endnote collection point.
- Footnotes/endnotes reuse the established `[^label]` / `[^label]:`
  syntax, distinguished by a `fn:`/`en:` label namespace rather than a
  new bracket form.
- Poetry layouts (`stacked`, `split`, `band`) are the one genuinely novel
  piece, since no prior art exists for them.

**2. Build the parsing layer on the `unified`/`remark` ecosystem
(`mdast`), not `markdown-it`.**

`remark-directive` already implements the `:::name {attrs}` syntax UEB-MD
relies on for every structural feature; `micromark-extension-footnote`
already implements footnote syntax. Choosing `remark` means most of
UEB-MD's parsing is composition of maintained plugins plus a thin
namespace/attribute layer, not a parser built from scratch. `mdast`'s
tree structure also matches the AST-to-AST transform `converters` needs
(mdast → Lexical JSON and back) far better than `markdown-it`'s flat
token stream would.

**3. Extend existing Lexical nodes with fields before introducing new
node types, and only introduce new types for genuinely new structures.**

- Footnote/endnote: one `FootnoteReferenceNode` with a `kind` field, not
  two node classes, since they're visually identical and differ only in
  collection point.
- Justify: no new node at all — Lexical's `ElementNode` already supports
  a `justify` format value.
- New node types are introduced only where nothing existing fits:
  `EndnoteCollectionNode`, `AppendixSectionNode`, `GhazalContainerNode`,
  `AttributionNode`, and extensions to `PoetryBlockNode`'s schema for
  layout/hemistich data.
- Every new node type is registered in `core` unconditionally; feature
  flags in `EditorProps` gate toolbar UI and import sanitization only —
  never registration. This preserves the existing project-wide rule that
  disabling a flag must never break deserialization of already-authored
  content.

**4. Split read-side rendering into its own `renderer` package, built on
`remark-rehype`, sharing the same `mdast` tree that `converters`
consumes — rather than treating rendering as an editor-only concern.**

`converters` maps UEB-MD ⇄ Lexical for editing. A separate concern —
turning UEB-MD into HTML/EPUB for actual reading — has no editor
dependency and shouldn't have one. Because both packages start from
identical `mdast` output, they can't silently drift apart in what syntax
each accepts. Each phase of implementation ships its `renderer` handler
alongside the corresponding `core`/`converters` work, not deferred to a
final integration phase, so "exported Markdown can be rendered later" is
continuously verified rather than discovered as a gap at the end.

**5. Treat poetry as the one phase requiring a mandatory pre-merge
checkpoint, gated by a throwaway rendering spike before schema
commitment.**

Every other UEB-MD feature has either an existing Lexical primitive to
extend or an established markdown convention to adapt. Poetry layouts
(specifically the `split` two-hemistich layout and script-aware
line-height behavior) have neither, and the node schema is expensive to
change once real manuscripts depend on it — so it gets a dedicated
prototype step and an explicit go/no-go gate that the other phases don't
require.

## Consequences

**Positive**

- Parsing/serialization work is mostly plugin composition on maintained
  libraries (`remark-directive`, footnote extensions) rather than a
  hand-rolled parser, reducing both build time and long-term maintenance
  surface.
- `.md` files exported from Likhari are genuinely portable — any
  UEB-MD-compliant tool can render them, not just Likhari's own
  importer — because the `renderer` package is validated independently
  against the same fixture corpus used for editor round-tripping.
- Extending existing nodes (footnote `kind` field, native `justify`
  format) instead of multiplying node types keeps the Lexical schema
  smaller and keeps the "registration ≠ feature availability" rule easy
  to reason about.
- Framework-agnostic `core`/`converters`/`renderer` work means the Vue
  and Web Component wrappers mostly need flag exposure, not new logic.

**Negative / risks accepted**

- UEB-MD is a bespoke extension with no existing ecosystem support
  beyond what `remark-directive`/footnote plugins provide generically —
  third-party tools won't understand the poetry containers or namespaced
  footnote labels without adopting this spec specifically.
- The `fn:`/`en:` label namespace and the `|` hemistich divider inside
  verse containers are custom parsing rules layered on top of
  `remark-directive`/footnote extensions, and need their own test
  coverage for edge cases (e.g., `|` colliding with table syntax) since
  they aren't covered by the upstream plugins' own test suites.
- Running `converters` and `renderer` work in parallel per phase (rather
  than sequentially) requires coordinating fixture corpus changes across
  both, or the two packages can still drift silently despite sharing
  `mdast` — the shared AST reduces this risk but doesn't eliminate the
  need for the independent-parser check in the Phase 0 checkpoint.
- Poetry's dedicated spike/checkpoint adds calendar time before that
  phase can merge; accepted as a smaller cost than reworking a committed
  schema against real content later.

## Alternatives Considered

- **`markdown-it` as the parsing base** — rejected primarily because its
  token-stream model is a worse fit for the AST-to-AST transform
  `converters` needs, despite a smaller bundle size and a mature plugin
  ecosystem of its own.
- **Inventing bespoke bracket/fence syntax per feature** instead of a
  generic attribute-list + directive mechanism — rejected as it would
  multiply parser surface area for no benefit over reusing
  `remark-directive` for every structural feature.
- **A single `renderer`-inside-`converters` design** (rendering as an
  editor-package concern) — rejected because it would implicitly couple
  standalone rendering to Lexical availability, undermining the
  requirement that exported Markdown be renderer-agnostic.
- **New node classes for every footnote/endnote and alignment case**
  instead of field extensions on existing nodes — rejected as
  unnecessary schema growth for visually/structurally identical
  concepts that differ only in metadata.
